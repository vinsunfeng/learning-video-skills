   （临时的）；长期修复应把 python3.11 前置进 PATH 或重装 yt-dlp。

## 附：minimax MCP「挂了」的诊断与修复（同日晚）

E2E 里 agent 报「minimax 视觉 MCP 进程挂了」。逐层排查：

| 假设 | 验证 | 结论 |
|---|---|---|
| MCP 服务器坏 | 手动 stdio initialize 握手 → 正常回包（Minimax v1.29.1） | 服务器健康 |
| hermes 连不上 | `hermes mcp test minimax` → ✓ Connected、2 工具发现 | 框架健康 |
| gateway 持有死句柄 | `hermes gateway restart` 后重测 → 同样失败 | 无关 |
| 缓存/配置 | schema cache 正常、config 未变 | 无关 |
| **hermes 源码** | 读 `tools/mcp_tool.py:2988 _stdio_children_dead` | **bug** |

**Bug**：`_stdio_children_dead` 把活/死两个返回值写反了——pid 活着 `return True`、
循环结束 `return True`，中间还有一个不可达的 `return False`。后果：**pids 非空时
永远返回 True**，任何 stdio MCP 调用都 fast-fail「has exited」，与子进程死活无关。
（v0.20.5 的回归；8/8 在 v0.19 上 understand_image 实测可用。`mcp test` 走独立
路径所以一直显示健康——同一个工具体系里又一个「仪器和仪器打架」。）

**修复**：交换返回值（备份在 `mcp_tool.py.bak-20260828`）。修后用**内容已知的帧**
（05:18 分辨率节点画面）实测：hermes 经 minimax MCP 逐字读出节点名、1280x720、
1024x1024 自定义参数、Set_width/Set_height、RunningHub 界面、底部坐标栏 0.25 缩放
——与抽帧时的已知事实逐项吻合。

> ⚠️ 此补丁在 hermes 升级时会被覆盖；上游应修 `mcp_tool.py` 的
> `_stdio_children_dead`（活/死返回值反了）。

## 附二：hermes 内置视觉挂自有 provider（同日晚，回答「能不能不绕 MCP」）

能。hermes v0.20 的内置 `vision_analyze` 由 `auxiliary.vision.provider` 路由：
auto 顺序是「主 provider → openrouter → nous」——本机主 provider 是 deepseek
（**文本模型读不了图**）、nous 欠费未配置 ⇒ 内置视觉一直不可用，才只剩 MCP 一条路。

本机可用组合（已配置并实测）：

- provider 写 **`minimax-cn`**（不是 `minimax`——那是国际端点 api.minimax.io，
  用户的 `sk-cp-*` Token Plan key 只在 CN 端点 api.minimaxi.com 有效，401 实证）
- 默认模型 MiniMax-M3，路由 `https://api.minimaxi.com/anthropic`
- **配置有两层**：全局 `~/.hermes/config.yaml` 和 `~/.hermes/profiles/wiki/config.yaml`，
  profile 覆盖全局——只改全局不生效（踩过）
- 实测：-z 会话内 `vision_analyze` 读已知帧，节点结构/字段/连线全对
  （小字有误差：workflow ID 末几位读错——「专名以 OCR/画面逐字为准」规则仍必要）
- 修改可逆：两份 config 各有 `.bak-vision-20260828` 备份

至此 hermes 读图有两条等价管道：内置 vision_analyze（minimax-cn）和
MCP understand_image——底层同为 MiniMax-M3、同一账号。
